# 16 Navbar + Mosque-context bug fixes — bugs found

| ID | What | How fixed |
|---|---|---|
| **B16-1** | `frontend/src/components/Common/Navbar.jsx` had the mosque selector shown at `xl:` (≥ 1280px) and Login/Register buttons shown at `lg:` (≥ 1024px). At the lg breakpoint when the user is logged out + a mosque is selected, the logo's longer mosque-name text + 4 primary links + 2 dropdowns + mosque selector + 2 auth buttons all tried to fit in one row, causing the **More** dropdown to wrap below the others and look misaligned | Hid the mosque selector at the lg breakpoint when the user is **not** logged in (only shows at `xl:`). When logged in, the avatar (10×10 circle) takes much less space than the two auth buttons, so the selector fits at lg. Also tightened the primary nav's `flex-nowrap` so links don't wrap, narrowed the logo block at lg (`max-w-[7rem]`), and reduced Login/Register button padding. |
| **B16-2** | `frontend/src/context/MosqueContext.jsx` only initialized its `activeMosqueId` state from `localStorage` **once** on mount via `useState(() => getActiveMosqueId() || '')`. After `AuthContext.login()` updated `localStorage.activeMosqueId`, the React state in `MosqueContext` stayed stale — so the navbar continued to show the auto-picked first mosque, not the user's home masjid | Added `useContext(AuthContext)` import + a `useEffect([user?._id, user?.mosqueId])` that calls `setActiveMosqueIdState(user.mosqueId)` whenever the user's `mosqueId` changes (login or refresh). The `setActiveMosqueId` localStorage write happens in `AuthContext` already; we now also push it into the React state. |
| **B16-3** | `backend/services/fundRequestsService.js#notifyCommittee` used `Promise.allSettled` to send emails to all committee members, but logged nothing about how many members were fetched or how many sends succeeded vs failed. When the user reported emails not arriving, the server log was silent — no way to tell whether the lookup returned 1 member (stale DB) or 4 members with 4 failed sends (SMTP issue) | Added structured logging: `[notifyCommittee] request=<id> mosqueId=<id> members=<N> emails=<list>` on dispatch + `[notifyCommittee] sent=<N> failed=<N>` after, with per-failure error messages on subsequent lines. The seed wires all 4 Al-Noor committee members (1 synthetic + 3 Gmail), so if `members !== 4` the DB is stale and needs `node utils/seed.js`. |
| **B16-4** | `frontend/src/components/User/Pages/MyRequests.jsx`, `frontend/src/components/Admin/Pages/FundRequests.jsx`, and `frontend/src/components/Committee/Pages/Dashboard.jsx` all had `useEffect(() => { load() }, [showToast])` — only refetched on mount. When the user switched the active mosque in the navbar, none of the fund-request-related pages refetched their data | Added `activeMosqueId` to the dependency array of each `useEffect`. The pages now refetch whenever the user picks a different masjid. The data is unchanged for community users (filtered by userId) and for committee/admin (filtered by user.mosqueId), but the page visually reacts — which is what the user expects. |
| **B16-5** | The seed + live DB had `committee@emasjid.pk` (synthetic, non-existent domain) listed as an active Al-Noor committee member. When a fund request was submitted, `notifyCommittee` tried to send an email to `committee@emasjid.pk` that **bounced** with `Mail Delivery Subsystem: domain emasjid.pk couldn't be found`. The Gmail SMTP accepted the message (returned `sent=4`) but Google's post-send filter rejected delivery to that fake recipient — and the developer only saw the bounce in the From-address account's inbox, not the real Gmail accounts, so it looked like only 1 email was sent | (1) `backend/utils/seed.js` — `committee1` row now created with `isActive: false` so future reseeds never re-activate it. (2) `backend/utils/patch_committee_active.js` — one-shot script that marks all 4 synthetic `committee*@emasjid.pk` accounts `isActive: false`. (3) `backend/utils/sendEmail.js` — added optional `replyTo` parameter. (4) `backend/services/fundRequestsService.js#notifyCommittee` — passes `replyTo: process.env.COMMITTEE_REPLY_TO` so committee replies go to a real inbox. (5) `backend/.env` — added `COMMITTEE_REPLY_TO=pa672189@gmail.com`. After fix, `members=3 emails=wb494929@gmail.com,ara786125@gmail.com,dawood.ahmed786678@gmail.com` — all real inboxes. |
| **B16-6** | After B16-5, only `wb494929@gmail.com` (a developer's well-used Gmail) actually received the email. The other 2 committee Gmail inboxes (`ara786125@gmail.com`, `dawood.ahmed786678@gmail.com`) were newly-created accounts and Gmail's anti-spam silently dropped the message — no bounce, no Spam-folder entry, just nothing. The diagnostic log still showed `sent=3 failed=0` because Gmail's SMTP accepted the message; the failure was at the post-send delivery filter. | (1) `backend/utils/patch_committee_friends.js` — one-shot script that deactivates the 3 newly-created developer Gmail accounts (`wb494929`, `ara786125`, `dawood.ahmed786678`) and inserts 4 new committee accounts using established Gmail accounts from the developer's friends: `jackcanada333@gmail.com`, `jackcanada111@gmail.com`, `motivation4@gmail.com`, `haseeb102323@gmail.com` — all `role: committee`, `isActive: true`, `mosqueId: Al-Noor._id`, `password: committee123`. (2) `backend/utils/seed.js` — replaced the 3 old `realEmailCommittee*` rows with 4 friend Gmail accounts so future reseeds start with the same list. After fix, diagnostic log shows `members=4 emails=jackcanada333@gmail.com,jackcanada111@gmail.com,motivation4@gmail.com,haseeb102323@gmail.com sent=4 failed=0` — all 4 are real, established inboxes. |
